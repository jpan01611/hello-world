# Conventions & notes

## Agent rules

AI coding-agent rules live in [`AGENTS.md`](../AGENTS.md) (imported by
`CLAUDE.md`). Notably:

- **Agents must not `git commit` or `git push` on the author's behalf.** Commits
  and pushes are performed manually. Staging changes, showing diffs, and
  suggesting commit messages are fine — the actual commit/push is the author's.
- The **`next dev`-managed block** at the top of `AGENTS.md` is regenerated by
  Next.js on every `next dev`. Commit it alongside your work to keep the tree
  clean, rather than deleting it (it will just come back).

## Row Level Security (RLS)

RLS is enabled on every table, enforcing the strictest rules that don't break
the app:

- **`profiles`** — a user can read and update only their own row; rows are
  created by the `security definer` signup trigger (which bypasses RLS).
- **`images` / `captions`** — any authenticated user can read; only the creator
  can update or delete their own rows. Image insertion requires matching
  `created_by`; caption insertion also requires ownership of the parent post.
- **`votes`** — any authenticated user can read; only the owner can insert,
  update, or delete their vote, and a unique `(user, caption)` constraint caps
  it at one vote per caption. This is what enforces "only logged-in users can
  rate".

Storage buckets (`images`, `avatars`) have their own policies in
`0004_storage_policies.sql`: public read, authenticated insert/update.

Anonymous visitors use `public_featured_feed()`, a fixed, read-only
security-definer RPC returning post images, one featured caption, and its
aggregate score. It does not expose hidden captions, prompts, or voter IDs.
The raw-table read policies remain authenticated-only.

## Code style

- Comments explain *why*, not *what* — reserved for non-obvious decisions.
- Server-only secrets never get a `NEXT_PUBLIC_` prefix (that would expose them
  to the browser bundle).
- Ownership is enforced in **two** places — the server action *and* the RLS
  policy — so a bug in one layer doesn't become a security hole.

## Not yet implemented

- **Account deletion.** The Profile page offers sign-out only. Deleting an
  `auth.users` row requires the Supabase service-role key, which is
  intentionally not wired up in this project.
